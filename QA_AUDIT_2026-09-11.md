# ReviewEngine — QA Audit

**Date:** 2026-09-11
**Performed by:** Manual + automated QA pass (real browser, real API calls, real database inspection) against a locally-run instance of the app — not a code-reading exercise.
**Environment:** Backend `php artisan serve --port=8123` + `queue:listen` (Redis), Frontend `next dev --experimental-https` (port 3000), Postgres 16, Mailpit for outbound mail. This mirrors the project's own `frontend/playwright.config.ts` local dev pairing.
**Branch/commit:** `main`, latest local commit `1efc184 contact us page added`.

---

## 1. Executive summary

The application is in noticeably good shape at the code-hygiene and defense-in-depth level: the full Pest suite (338 tests) passes, cross-tenant isolation (Postgres RLS + app-layer scope), CSV-injection protection, per-permission API enforcement, login rate-limiting, and admin audit logging all held up under live, adversarial testing during this pass — see §4 "What already works."

However, this audit found **one critical, production-breaking defect**: real email verification (and three other account/billing notifications) silently never deliver once the app runs behind a real, out-of-process queue worker — which is exactly how this app's own docs (`QUEUE.md`, `STAGING_VERIFICATION.md`) say it must run everywhere outside the test suite. This is invisible to `php artisan test` because the test environment runs queued jobs synchronously in-process, masking the bug entirely. Left unfixed, a real customer who registers cannot verify their email through the product's own UI, and can therefore never start sending a single review request — the entire point of the product. **This should be the first thing fixed.**

Seven further issues were found, ranging from a real responsive-layout bug on the marketing homepage to UX rough edges (a form that wipes itself on error, a super-admin account that lands on the wrong screen after login). Full detail in §3.

Three areas — the AI compliance checker's actual pass/block judgment, a real Paddle checkout, and real Google OAuth — could not be exercised end-to-end because this local environment has no `ANTHROPIC_API_KEY`, `PADDLE_CLIENT_SIDE_TOKEN`, or `GOOGLE_CLIENT_ID`/`SECRET` configured. Everything reachable *without* those third-party credentials (validation, error handling, gating logic, RLS, the request/response shape of each integration) was verified directly.

## 2. Method

1. Ran the full backend automated suite (`php artisan test`) and the frontend e2e suite (`npx playwright test`) as a baseline before any manual testing.
2. Seeded three real demo accounts (super-admin, tenant owner, permission-restricted team member) via the repo's own `DemoAccountsSeeder`.
3. Walked every reachable screen as a real browser session: marketing site → registration → email verification → onboarding (plan, GBP connect, CSV import) → dashboard → templates/compliance → contacts (CSV import, quick-add) → reviews → analytics → settings (profile, sender identity, billing, team, webhooks/API) → admin (tenants, audit log, system health) → API docs.
4. For each flow, tested the happy path **and** adversarial/edge inputs: empty/invalid forms, SQL-injection and XSS payloads, CSV formula-injection payloads, cross-tenant IDOR attempts (forged tenant headers, another tenant's object IDs), permission-restricted access, invalid/expired tokens, and login brute-forcing.
5. For anything that looked wrong, traced it to the actual source line before recording it as a finding — every item below has a concrete file/line and a live repro, not a guess.

## 3. Findings (problems found), most severe first

### 🔴 Finding 1 — CRITICAL: Email verification (and 3 other account notifications) never actually deliver under a real queue worker

**Use case:** *"As a new tenant, I register, then click 'Resend verification email' (or receive the one sent at registration), and my inbox gets the email."*

**What happens instead:** The UI says "Verification email sent." The queue worker log shows the job completing with no error. **The email never arrives.**

**Repro (performed live):**
- Registered a fresh tenant, clicked "Resend verification email" in Settings.
- Confirmed Mailpit (the SMTP catcher) never received it.
- Ruled out a mail/SMTP misconfiguration: a direct `Mail::raw()` call and a `Notification::sendNow()` call (bypassing the queue) **both delivered instantly** to the same address.
- Only the **queued** delivery path silently fails.

**Root cause:** `App\Notifications\VerifyEmailAddress` implements `ShouldQueue`. Laravel's queue system automatically serializes the notification's `$notifiable` (a `User` Eloquent model) and re-fetches it by ID when the job runs in the worker process (`Illuminate\Queue\SerializesModels`). This app's Row-Level Security requires `app.current_tenant_id`/`app.is_admin` to be set on the database session before any tenant table can be read — and a real, separate worker process has neither set at that point. The lookup returns zero rows, and Laravel's documented behavior for a "missing model" during job unserialization is to **silently discard the job as if it succeeded** — no exception, no `failed_jobs` row, no log line.

Confirmed directly: `App\Models\User::find(171)` with no tenant context set returns `NULL`, reproducing exactly what the worker sees.

**Why the test suite (338/338 green) never caught this:** `phpunit.xml`/`.env.testing` set `QUEUE_CONNECTION=sync`, under which "queued" jobs run inline in the same request that already has tenant context — the bug can only appear when a job genuinely crosses a process boundary, i.e. every real deployment.

**Blast radius — every direct `$eloquentUser->notify(...)` call in the codebase (4 total, verified by full-repo search):**
| Notification | Call site | Effect if silently lost |
|---|---|---|
| `VerifyEmailAddress` | `app/Models/User.php:198` | **Confirmed broken live.** Tenant can never verify → permanently blocked from sending review requests. |
| `WelcomeEmail` | `AuthController.php:268` | Missed welcome email after first verification. |
| `GbpConnectionRevoked` | `GbpTokenRefresher.php:94` | Tenant's Google sync silently dies with no notice to fix it. |
| `SubscriptionRenewalReminder` | `SendRenewalReminders.php:196` | 10-day/5-day billing reminder emails never sent. |

By contrast, `TeamInviteReceived` (`TeamController.php:91`) uses `Notification::route('mail', $email)->notify(...)` — an ad-hoc route with no model to rehydrate — and **does** deliver correctly. This is the proven fix pattern, already used elsewhere in this codebase.

**Fix direction:** stop passing an Eloquent `User` as the notifiable for these four notifications; route them ad-hoc the same way `TeamInviteReceived` already does, passing plain scalars (email, name, etc.) instead of relying on the queue rehydrating a tenant-scoped model.

### 🟠 Finding 2 — Marketing homepage has a real horizontal-scroll bug at tablet width

**Use case:** *"A prospect opens the marketing site on an iPad or a large phone."*

At exactly 768px width (iPad Mini portrait, and anything in that range), the page gains an unwanted 50px of horizontal scroll.

**Root cause:** `Footer()` in `frontend/app/page.tsx` (~line 406) lays out its three link columns as `grid grid-cols-2 sm:grid-cols-3 gap-x-8`. At the `sm` breakpoint the "Contact" column has to fit the unbroken string `support@reviewengine24.com` (no `break-all`/`min-w-0`) in a track too narrow for it; the browser refuses to shrink the column below that word's width, so the whole grid overflows the page.

Confirmed precisely via a real device-profile browser check: `scrollWidth` 818px vs. `clientWidth` 768px, and the offending text run's own right edge measured at 817.6px. This is exactly what the project's own `e2e/marketing-visual.spec.ts` (tablet describe block) is currently failing on — a real, non-flaky failure.

**Fix:** add `break-all` (or wrap in a `min-w-0`/`truncate` container) to the footer's Contact column.

### 🟠 Finding 3 — Registration form wipes every field on any validation error

**Use case:** *"I fill out the signup form, make one mistake (e.g. my two passwords don't match), and fix just that."*

**What happens instead:** every field — name, business name, email, both password fields — is blanked, leaving only the red error text. The user has to retype the entire form.

**Root cause:** `frontend/app/(app)/register/RegisterForm.tsx`'s `Field` component renders a plain `<input>` with no `value`/`defaultValue` at all. React's `useActionState` re-render after *any* server response (a 422 or otherwise) resets every uncontrolled input to empty — this isn't limited to the password mismatch case, it will happen on a weak password, an already-registered email, or any other validation failure.

**Fix:** echo submitted values back via `defaultValue` (never for the password fields) from the server action's returned state.

### 🟠 Finding 4 — Super-admin login lands on the customer onboarding wizard, not the admin dashboard

**Use case:** *"I log in with the operator/super-admin account to check on tenants."*

**What happens instead:** landed on "Let's get you set up — Step 1 of 5: Plan — Pick a plan to get started... Start free trial" — the customer-only trial/pricing wizard. The real admin panel (`/admin`) works fine once navigated to directly; the bug is purely the post-login landing route.

**Root cause:** `frontend/app/(app)/dashboard/page.tsx:30-37` unconditionally redirects to `/onboarding` whenever `onboarding_completed_at` isn't set — and it deliberately never is for an admin-type tenant (admins don't have a plan/trial to complete). The login response already carries `user.is_admin`; the dashboard gate just never checks it.

**Fix:** branch on `is_admin`/tenant type before the onboarding-completion redirect and send admin accounts straight to `/admin`.

### 🟡 Finding 5 — No queue prioritization: transactional email can be starved by bulk drip retries

**Use case (architectural, not a one-off bug):** *"A tenant's contact list has some incomplete/misconfigured entries; meanwhile a different tenant needs their verification email fast."*

`App\Jobs\SendReviewRequest` self-requeues indefinitely (no max-attempts/give-up) for a contact that can structurally never succeed (e.g. no email address at all, or no verified sender identity yet). It runs on the exact same unprioritized Redis queue (`default`) as every transactional notification (`VerifyEmailAddress`, `TeamInviteReceived`, etc.). Under any real backlog, low-value bulk retries can delay time-critical mail for *every* tenant sharing the worker pool, not just the misconfigured one. Directly observed in this environment: a verification-email job sat behind dozens of drip-retry jobs in the live Redis queue.

**Fix:** put transactional notifications on a separate, higher-priority queue (`->onQueue('transactional')`, worker run as `--queue=transactional,default`); give `SendReviewRequest`'s retry branches a cap instead of an unbounded self-requeue.

---

### 🟡 Finding 6 — GBP OAuth connect has no guard for missing/misconfigured Google credentials

**Use case:** *"I click 'Connect Google Business Profile' during onboarding."*

If `GOOGLE_CLIENT_ID`/`SECRET` are unset or invalid, the user is redirected straight to Google's own raw error page ("Missing required parameter: client_id") instead of a friendly in-app message. `GbpController::connect()` builds the OAuth redirect unconditionally with no config check.

**Fix:** guard with a config check before building the redirect; return a friendly 503/error the frontend can render inline.

---

### 🟡 Finding 7 — "Continue to checkout" is silently disabled with no explanation if the Paddle client-side token is missing

**Use case:** *"I try to subscribe from Settings → Billing."*

The button (`frontend/app/(app)/settings/SubscribeForm.tsx:163`) is disabled whenever `NEXT_PUBLIC_PADDLE_CLIENT_SIDE_TOKEN` is empty, with zero message anywhere explaining why. Low real-world likelihood (a real deploy should always have this baked in), but if it ever slips, a paying customer sees a dead button with no feedback.

**Fix:** render an inline note ("Checkout is temporarily unavailable") when the token is missing.

---

### ⚪ Finding 8 — (local-dev only) `APP_URL` mismatch makes real email links dead in this setup

`backend/.env` has `APP_URL=https://localhost:8443`, but the backend actually runs on `:8123` in this project's own documented local dev pairing. Every mail-generated link (verification link, mail header logo) points at the dead port. Purely a stale local `.env` value — not scored as a product defect, flagged so the next person testing verification locally doesn't lose time on it as I did.

---

### ⚪ Observation — possible dropped characters typing quickly into the Template message box (unconfirmed)

Twice, fast/scripted typing into the Templates "Message" textarea dropped one character (e.g. "10% off" → "10% ff"). Could not cleanly isolate whether this is a real React re-render race in that field or an artifact of the browser-automation tool's synthetic typing outrunning input events — attempts to reproduce on other fields were inconclusive. **Recommend:** a human manually types a sentence with "%" quickly into the Template editor and checks nothing is dropped. Not counted in the findings total below.

## 4. What already works (verified live, not assumed)

- **Cross-tenant isolation (RLS + app-layer scope), tested adversarially:** a second real tenant's API token could not read another tenant's contact by ID (404, not a data leak), could not list any of their contacts, got 403 on admin-only routes, and a forged `X-Tenant-Id` header was correctly ignored. Direct SQL confirmed a tenant's raw `personal_access_tokens` query only ever returns its own row.
- **SQL injection:** parameterized everywhere tested (`sort`, `search` params with injection payloads returned clean empty results, no error leakage, table intact afterward).
- **CSV formula-injection guard:** a CSV with `=cmd|...`, `+2+3+cmd|...`, `-1+1`, `@SUM(1+1)` payloads was correctly auto-corrected (leading `'` prefix) both in the UI preview **and** confirmed in the persisted database rows.
- **Contact form:** proper server + native validation, a working honeypot, and confirmed HTML-escaping of an injected `<script>` payload in the resulting email.
- **Login rate limiting:** 5 failed attempts succeed, the 6th+ correctly returns 429.
- **Permission system:** a team member scoped to `reviews`+`analytics` only gets a graceful "Page not found" on `/contacts` in the UI and a real `403` from the API on `/contacts` and `/templates`, while `/reviews` correctly returns `200`.
- **Quick-add (public, no-login link):** works end-to-end once the owner's email is verified; an invalid/garbage token shows a clean "This link isn't active" message rather than an error page.
- **Admin panel:** tenant list/filter, per-tenant detail with real payment history (including a failed-payment reason), and the audit log correctly recording every admin read with a real timestamp — matches `DATABASE.md`'s "every admin cross-tenant read writes an audit_log row" requirement.
- **System health page:** correctly detected that Horizon wasn't running in this environment (this session used plain `queue:listen` instead) and surfaced a real warning.
- **Onboarding wizard, CSV import, template editor, dashboard, settings tabs:** all render and function correctly for the tested (non-edge-case) paths.

## 7. Recommended priority order

1. **Finding 1** (email verification silently fails under a real worker) — fix before anything else ships; it blocks the core product loop for every real tenant.
2. **Finding 2** (marketing page horizontal scroll) — quick, high-visibility fix on the one page every prospect sees first.
3. **Finding 4** (admin lands on wrong screen) and **Finding 3** (register form wipes itself) — both small, contained fixes with real day-to-day friction.
4. **Finding 5** (queue prioritization) — architectural, worth doing before real production traffic makes the backlog scenario actually happen.
5. Findings 6–8 — low severity, fix opportunistically.
